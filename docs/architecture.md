# 技術仕様書 (Architecture Design Document)

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン |
|------|-----------|
| Node.js | v24.11.0 |
| TypeScript | 5.x |
| npm | 11.x |

### フレームワーク・ライブラリ

| 技術 | バージョン | 用途 | 選定理由 |
|------|-----------|------|----------|
| Commander.js | ^13.1.0 | CLIコマンド・オプションのパース | PRDで選定済み。サブコマンド(`add`/`list`/`start`等)の定義が宣言的に書け、学習コストが低い(ユーザープロフィール編集機能の実装時に、当時のnpmレジストリ最新版として^13.1.0を採用) |
| simple-git | ^3.x | Gitブランチの作成・切り替え・状態確認 | Promiseベースで`git`コマンドをラップでき、`task start`のブランチ自動作成をシンプルに実装できる |
| cli-table3 | ^0.6.x | `task list`の表形式出力 | 列幅の自動調整とUnicode罫線に対応し、PRDのUI要件(表形式一覧)を満たす |
| chalk | ^4.1.2 | ステータス・優先度の色分け表示 | TTY判定による自動フォールバックを内蔵し、パイプ実行時にANSIコードが混入しない。当初はESM専用のv5系を想定していたが、本プロジェクトの`tsconfig.json`(`module: ESNext`, `moduleResolution: bundler`)とNode実行時の相互運用性を優先し、CJS/ESM両対応のv4系に決定 |

### 開発ツール

| 技術 | バージョン | 用途 | 選定理由 |
|------|-----------|------|----------|
| Vitest | ^2.x | ユニットテスト・統合テスト | ESM/TypeScriptとの親和性が高く、Node.js標準のtest runnerより高速に実行できる |
| ESLint | ^9.x | 静的解析 | TypeScript ESLintと組み合わせ、型不整合や未使用変数をコミット前に検出する |

## アーキテクチャパターン

### レイヤードアーキテクチャ

```
┌─────────────────────────┐
│   CLIレイヤー             │ ← ユーザー入力の受付と表示(Commander.js)
├─────────────────────────┤
│   サービスレイヤー        │ ← ビジネスロジック(TaskManager)
├─────────────────────────┤
│   Git連携レイヤー         │ ← Gitブランチ操作(GitService)
├─────────────────────────┤
│   データレイヤー          │ ← データ永続化(FileStorage)
└─────────────────────────┘
```

#### CLIレイヤー
- **責務**: コマンドライン引数の受付、バリデーション、結果・エラーの表示
- **許可される操作**: サービスレイヤー(TaskManager)の呼び出し
- **禁止される操作**: FileStorage・GitServiceへの直接アクセス

#### サービスレイヤー
- **責務**: タスクのCRUD、ステータス遷移、Git連携のオーケストレーション
- **許可される操作**: Git連携レイヤー・データレイヤーの呼び出し
- **禁止される操作**: CLIレイヤーへの依存(標準出力への直接書き込みをしない)

#### Git連携レイヤー
- **責務**: Gitリポジトリ判定、ブランチ作成・切り替え、ブランチ名生成
- **許可される操作**: simple-git経由でのGitコマンド実行
- **禁止される操作**: タスクデータ(tasks.json)への直接アクセス

#### データレイヤー
- **責務**: `tasks.json` の読み込み・書き込み・バックアップ
- **許可される操作**: ファイルシステムへのアクセス
- **禁止される操作**: ステータス遷移などのビジネスロジックの実装

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| タスクデータ(Task, TaskStore) | ローカルファイル | JSON(`.task/tasks.json`) | PRDの結論通りMVPはJSONを採用。Gitで管理可能で追加の依存を必要としない |
| バックアップ | ローカルファイル | JSON(`.task/backups/tasks.json.N`) | 障害時の復元用に直近世代を保持する |

### バックアップ戦略

- **頻度**: `tasks.json` への書き込みが発生するたび(コマンド実行ごと)
- **保存先**: `.task/backups/` ディレクトリ
- **世代管理**: 最新5世代を保持し、6世代目以降は最古のものから削除(ローテーション方式)
- **復元方法**: `tasks.json` のJSONパースに失敗した場合、CLIが `.task/backups/tasks.json.1` からの復元を確認プロンプトで提案する

## パフォーマンス要件

### レスポンスタイム

| 操作 | 目標時間 | 測定環境 |
|------|---------|---------|
| `task add` / `task done` / `task delete` 等の単一タスク操作 | 100ms以内 | CPU Core i5相当、メモリ8GB、SSD |
| `task list`(タスク1000件) | 1秒以内 | 同上、ダミーデータ1000件を`tasks.json`に投入して計測 |
| `task start`(ブランチ作成・切り替え含む) | 500ms以内 | 同上、ローカルGitリポジトリに対して計測 |

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| メモリ | 100MB | タスク1000件程度をオンメモリで扱う軽量CLIのため、大きな上限は不要 |
| ディスク | 10MB | `tasks.json`本体とバックアップ5世代を合わせても数百KB〜数MB程度に収まる想定 |

## セキュリティアーキテクチャ

### データ保護

- **暗号化**: MVP(P0)スコープでは機密情報(トークン等)を扱わないため暗号化は行わない
- **アクセス制御**: `.task/tasks.json` は作成時に `chmod 600` 相当のパーミッション(所有者のみ読み書き)を設定する
- **機密情報管理**: P1で追加するGitHub Personal Access Tokenは、`.task/tasks.json` には保存せず、OS標準の認証情報ストアまたはGit管理対象外の設定ファイルに保存する設計とする(実装はP1着手時に別途詳細化)

### 入力検証

- **バリデーション**: タスクタイトルは1〜200文字、前後の空白をトリムしてから検証する
- **サニタイゼーション**: タイトルはブランチ名生成時にスラッグ化(英数字・ハイフンのみに変換)し、シェルコマンドインジェクションを防ぐためsimple-gitの引数配列渡しAPIを使用する(シェル経由の文字列結合は行わない)
- **エラーハンドリング**: バリデーションエラーは内部のスタックトレースを含めず、ユーザー向けメッセージのみを表示する

## スケーラビリティ設計

### データ増加への対応

- **想定データ量**: 個人開発者の利用を想定し、1000〜1万件のタスクまでを許容範囲とする
- **パフォーマンス劣化対策**: MVPはファイル全体読み込み方式のため、1万件を超える規模でパフォーマンス劣化が確認された場合はSQLiteへの移行を検討する(PRDの技術的検討事項に準拠)
- **アーカイブ戦略**: `archived` ステータスのタスクは `task list` のデフォルト表示から除外することで、一覧表示の実用上の見やすさを保つ(データ自体は`tasks.json`に残す)

### 機能拡張性

- **プラグインシステム**: MVPでは実装しないが、TaskManagerのメソッドをインターフェース化しておくことで、将来的なコマンド拡張(P1のGitHub連携等)を追加しやすい構造とする
- **設定のカスタマイズ**: MVPでは固定動作とし、将来的に `.task/config.json` での設定カスタマイズ(P2)を見据えた拡張ポイントをFileStorageに用意する
- **API拡張性**: P1のGitHub連携時は、GitServiceと同階層に`GitHubService`を追加し、TaskManagerから呼び出す構成を想定する

## テスト戦略

### ユニットテスト
- **フレームワーク**: Vitest
- **対象**: TaskManager(CRUD・ステータス遷移)、GitService(ブランチ名生成)、FileStorage(アトミック書き込み・バックアップローテーション)
- **カバレッジ目標**: サービスレイヤー・データレイヤーで80%以上

### 統合テスト
- **方法**: Vitest上で一時ディレクトリ・一時Gitリポジトリを作成し、実際のファイルI/Oとgitコマンドを実行して検証する
- **対象**: `task add → list`、`task start`(ブランチ作成)、Gitリポジトリ外での`task start`のフォールバック動作

### E2Eテスト
- **ツール**: Vitest + Node.jsの`child_process`でビルド済みCLIバイナリを実行
- **シナリオ**: `add → start → done` の一連のフロー、1000件データでの`task list`のレスポンスタイム測定

## 技術的制約

### 環境要件
- **OS**: macOS, Linux, Windows(Git Bash / WSL2)
- **最小メモリ**: 256MB(Node.jsランタイム込み)
- **必要ディスク容量**: 50MB(node_modules込み)
- **必要な外部依存**: Git本体(`git`コマンドがPATH上に存在すること)

### パフォーマンス制約
- Gitリポジトリでない環境では`task start`のブランチ作成機能は動作せず、ステータス更新のみのフォールバック動作となる
- ネットワークアクセスを必要とする機能(P1のGitHub連携)はMVPには含まれず、オフライン環境でも全P0機能が動作する

### セキュリティ制約
- CLIはローカル実行を前提とし、認証・認可の仕組みは持たない(マルチユーザー環境での利用は想定しない)
- Personal Access Tokenを扱うP1機能実装時は、トークンのログ出力・エラーメッセージへの混入を禁止する
