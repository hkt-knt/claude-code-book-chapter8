# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**TaskCLI** - Gitと一体化したタスク管理CLIツール

### プロダクトコンセプト
- **ターミナル完結**: コードを書く、タスクを確認する、タスクを更新する、すべてをターミナルの中だけで完結させ、ブラウザやGUIツールへの切り替えを発生させない
- **Gitとの一体化**: タスクとGitブランチを1対1で紐付け、コミット・マージ・PRといったGit操作とタスクのステータスを自動的に連携させる
- **開発フローへの溶け込み**: 「タスク開始→ブランチ作成→コミット→PR→マージ→タスク完了」という一連の流れを自動化・支援し、手作業によるステータス更新の漏れをなくす

### プロダクトビジョン
TaskCLIは、開発者がターミナルから一度も離れることなくタスク管理を完結できる世界を目指す。GUIのタスク管理ツールとターミナルを往復するたびに発生する集中力の途切れをなくし、タスクとコードの結びつきを常に明確にする。Gitのブランチ操作やコミット、PR作成といった日常的な開発フローの中にタスク管理を溶け込ませることで、開発者は管理作業ではなく本質的なコーディングに集中できるようになる。小規模チームにおいても、JiraやAsanaのような重量級ツールを持ち込むことなく、軽量にチームの作業状況を可視化できる。

### 目的
- 画面切り替えによる集中力の途切れをなくし、開発者の生産性を向上させる
- タスクとGitブランチ・コミット・PRを自動連携させ、「今どのタスクで作業しているか」を常に明確にする
- タスク完了に伴う定型作業（ステータス更新、PR作成、タスククローズ）を自動化する
- 小規模チームがGUIツールなしで、CLI上でチームの作業状況を把握できるようにする

## ターゲットユーザー

### プライマリーペルソナ: 個人開発者(28歳、フリーランスエンジニア)
- 複数のプロジェクト(3-5個)を並行して受託・個人開発している
- 開発歴5年以上、ターミナル操作・Git操作に習熟している
- タスクが頭の中だけで管理されており、「このプロジェクトで次何をやるんだっけ」となることが多い
- GitHub Issuesは使っているが、ローカルでの作業(ブランチ、コミット)とは連携していない
- **現在の課題**: ターミナルでコードを書き、ブラウザでタスク管理ツールを開き、また戻る、という切り替えを1日20回以上行っており、そのたびに集中が途切れる
- **期待する解決策**: ターミナルの中でタスクを追加・確認・完了でき、`task start` するだけでブランチ作成まで自動でやってくれること
- **1日の典型的なワークフロー**: 朝に `task list` でその日のタスクを確認 → `task start` でブランチを切って作業開始 → コミットを重ねる → `task done` で完了処理

### セカンダリーペルソナ: 小規模チームのテックリード(35歳)
- スタートアップで2-5人のチームをリードしている、開発歴10年以上
- チームメンバーが今何をやっているかをリアルタイムに把握したいが、GUIツールを開かないと分からない
- JiraやAsanaは小規模チームには機能が過剰で、導入・運用コストが見合わない
- **現在の課題**: 朝会でのタスク確認に時間がかかりすぎる、GitHubのIssue進捗とタスク管理ツールの進捗がずれる
- **期待する解決策**: CLIで一発でチーム全体のタスク状況を確認でき、GitHubとの連携で進捗が自動更新されること

## 成功指標(KPI)

### プライマリーKPI
- 導入継続率: 紹介した開発者10人のうち3人以上が1週間以上継続利用する(リリース後1ヶ月で測定)
- タスク管理にかかる時間: 従来のGUIツール利用時と比較して50%削減(ユーザーへのヒアリングで測定)
- アクティブユーザー数: リリース後3ヶ月で100人(npmダウンロード数・GitHub Star数から推定)

### セカンダリーKPI
- Net Promoter Score(NPS): 30以上(リリース後3ヶ月時点でアンケート実施)
- 1ヶ月後の継続利用率: 60%以上(コマンド実行ログの匿名集計、オプトイン制)
- GitHub Stars: リリース後6ヶ月で500

## 機能要件

### コア機能(MVP)

#### 1. タスクの基本操作(CRUD)

**ユーザーストーリー**:
個人開発者として、頭の中だけでタスクを管理する状態から抜け出すために、ターミナルからタスクを追加・一覧表示・詳細確認・完了・削除できる機能が欲しい

**受け入れ条件**:
- [ ] `task add "<タイトル>"` でタスクを追加でき、一意なIDが自動採番される
- [ ] `task list` で全タスクをID・ステータス・タイトル・紐づくブランチの一覧表示できる
- [ ] `task show <id>` で指定タスクの詳細(作成日時、ステータス、ブランチ、コミット履歴)を表示できる
- [ ] `task done <id>` でタスクを完了ステータスに変更できる
- [ ] `task delete <id>` でタスクを削除でき、削除前に確認プロンプトが表示される
- [ ] 存在しないIDを指定した場合、分かりやすいエラーメッセージが表示される

**優先度**: P0(必須)

#### 2. タスクとGitブランチの自動連携

**ユーザーストーリー**:
個人開発者として、今どのタスクのためにどのブランチで作業しているか分からなくなる状態を避けるために、タスク開始時に自動でブランチが作成・切り替えされる機能が欲しい

**受け入れ条件**:
- [ ] `task start <id>` で `feature/task-<id>-<スラッグ化されたタイトル>` 形式のブランチが自動作成され、切り替わる
- [ ] `task start <id>` 実行時にタスクのステータスが自動的に `in_progress` に変わる
- [ ] 対象タスクに紐づくブランチが既に存在する場合は、新規作成せず既存ブランチに切り替える
- [ ] Gitリポジトリでないディレクトリで実行した場合、エラーメッセージを表示しGit連携機能を無効化した状態で継続できる
- [ ] コミットメッセージに `Task #<id>` の情報を自動付与するオプションを提供する

**優先度**: P0(必須)

#### 3. タスクのステータス管理

**ユーザーストーリー**:
個人開発者として、タスクの進行状況を正確に把握するために、タスクが `open` → `in_progress` → `completed` → `archived` というステータスを持ち、それぞれのステータスに応じたフィルタ表示ができる機能が欲しい

**受け入れ条件**:
- [ ] タスクは `open`(新規)、`in_progress`(作業中)、`completed`(完了)、`archived`(アーカイブ)の4つのステータスを持つ
- [ ] 新規作成したタスクのデフォルトステータスは `open` である
- [ ] `task list --status <status>` で指定ステータスのタスクのみ絞り込み表示できる
- [ ] ステータス遷移は `open → in_progress → completed → archived` の順を基本としつつ、`task status <id> <new-status>` で任意のステータスへ直接変更できる

**優先度**: P0(必須)

#### 4. シンプルなタスク一覧表示

**ユーザーストーリー**:
テックリードとして、朝会でのタスク確認を素早く終えるために、ID・ステータス・タイトル・ブランチ名が一目で分かる表形式の一覧が欲しい

**受け入れ条件**:
- [ ] `task list` はID、Status、Title、Branchの列を持つ表形式で出力される
- [ ] ステータスごとに色分け表示される(ターミナルがカラー表示に対応している場合)
- [ ] タスクが0件の場合、その旨をメッセージで表示する
- [ ] 1000件のタスクがあっても1秒以内に一覧表示が完了する

**優先度**: P0(必須)

### CLIインターフェース(該当する場合)

```bash
# タスクの基本操作
task add "ユーザー認証機能の実装"
task list
task list --status in_progress
task show 1
task done 1
task delete 1

# Gitブランチ連携
task start 1
# 自動で feature/task-1-user-authentication ブランチを作成・切り替え

git commit -m "Add login endpoint"
# コミットメッセージに Task #1 の情報が自動で追記される（オプション有効時）

# ステータス変更
task status 1 archived
```

### 将来的な機能(Post-MVP)

#### 5. GitHub Issuesとの連携

`task sync` でローカルタスクとGitHub Issuesを双方向同期し、`task import --github` で既存Issueをタスクとして取り込む。

**優先度**: P1(重要)

#### 6. タスク完了時の自動処理

`task done <id>` 実行時に、ブランチのmainへのマージ、リモートへのプッシュ、GitHub PRの自動作成(オプション)、タスクステータスの `completed` への変更を一括で行う。

**優先度**: P1(重要)

#### 7. タスクの絞り込み・検索

`task list --assignee me` や `task search "<キーワード>"` によるタスクの絞り込み・全文検索。

**優先度**: P1(重要)

#### 8. 優先度と期限の管理

`task add --priority high --due <date>` による優先度・期限の付与と、`task list --sort priority` によるソート表示。

**優先度**: P1(重要)

#### 9. チーム機能

`task list --team` によるチームメンバー全員のタスク一覧表示、`task assign <id> @<user>` によるタスクアサイン。

**優先度**: P2(できれば)

#### 10. カレンダー表示

`task calendar --week` / `task calendar --month` による期限ベースのカレンダー表示。

**優先度**: P2(できれば)

#### 11. 作業時間の記録

`task start` から `task done` までの経過時間を自動計測し、タスクごとの作業時間を記録する。

**優先度**: P2(できれば)

#### 12. タスクのテンプレート

`task template create <name>` で定型タスクのテンプレートを作成し、`task add --template <name>` で再利用する。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- コマンド実行時間: 100ms以内(平均的なPC環境、体感で即座に反応するレベル)
- タスク一覧表示: タスク数1000件でも1秒以内に表示完了
- Git連携処理(ブランチ作成・切り替え): 500ms以内

### ユーザビリティ
- 初めて使う人でも5分以内に基本操作(add/list/start/done)を習得できる
- `task --help` および各サブコマンドの `--help` で全機能を確認できる
- エラーメッセージには、原因と次に取るべきアクションを明記する(例: 「Gitリポジトリが見つかりません。`git init` を実行するか、既存のリポジトリ内で実行してください」)

### 信頼性
- タスクデータの損失がないよう、書き込み前に自動バックアップ(直近5世代)を保持する
- タスク削除やステータスの一括変更など、取り消しの効かない操作の前には確認プロンプトを表示する
- 予期しないエラー発生時、タスクデータファイルが破損しないようアトミックな書き込みを行う

### セキュリティ
- GitHub連携で使用するPersonal Access Tokenは平文でリポジトリにコミットされる場所(`.task/tasks.json`等)に保存しない
- トークンはOS標準の認証情報ストア、または `.env` 等のGit管理対象外ファイルに保存する

### スケーラビリティ
- MVPはJSON(`.task/tasks.json`)でのデータ保存とし、タスク件数が増加しパフォーマンス上の課題が出た場合はSQLiteへの移行を検討できる設計とする
- 将来的なプラグインシステム・カスタムコマンド追加を見据え、コア機能と拡張機能を疎結合に保つ

## スコープ外

MVPにおいて明示的にスコープ外とする項目:
- GitHub Issues以外の外部ツール連携(Jira、Trello、Asana等とのインポート/エクスポート)
- GitLab、Bitbucketなど、GitHub以外のホスティングサービスとの連携
- 専用クラウドサービスによるチーム間同期(MVPはGit経由のファイル共有のみ)
- 有料プラン・課金機能
- GUI/Webダッシュボード
- Slack・Discordなどチャットツールとの通知連携
